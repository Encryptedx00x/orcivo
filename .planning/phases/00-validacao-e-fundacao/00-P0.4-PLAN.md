**Parte 2 — GitHub Actions workflows:**

**`.github/workflows/backend.yml`:**
```yaml
name: Backend CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  ci:
    name: Lint, Typecheck & Build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 9

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'pnpm'

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Lint
        run: pnpm turbo run lint --filter=@orcivo/backend

      - name: Typecheck
        run: pnpm turbo run typecheck --filter=@orcivo/backend

      - name: Build
        run: pnpm turbo run build --filter=@orcivo/backend
```

**`docs/decisions/ADR-001-monorepo-turborepo.md`** — Monorepo com Turborepo + pnpm workspaces. Decisão: Turborepo para pipeline de build/lint/test; pnpm workspaces para dependências. Trade-off: overhead de configuração vs. ganho de cache e execução paralela.

**`docs/decisions/ADR-002-backend-nestjs.md`** — NestJS como framework backend. Contexto: precisa de estrutura modular, suporte a DI, decorators, e ecosystem maduro para TypeScript. Decisão: NestJS com Prisma como ORM. Trade-off: mais estrutura que Express/Fastify puro, mas produtividade maior em longo prazo.

**`docs/decisions/ADR-003-mobile-expo.md`** — React Native + Expo SDK. Contexto: app mobile para Android (iOS na Fase 7). Decisão: Expo para DX mais rápida, EAS Build para distribuição, TypeScript obrigatório. Trade-off: sem acesso a módulos nativos customizados sem ejetar; aceitável para o escopo planejado.

**`docs/decisions/ADR-004-web-nextjs.md`** — Next.js para o web app. Contexto: surface web de gestão (PC) precisa de SSR/SSG e routing. Decisão: Next.js App Router + TypeScript + Tailwind + shadcn/ui. Trade-off: React Server Components têm curva de aprendizado, mas o ecossistema é maduro.

**`docs/decisions/ADR-005-database-postgresql.md`** — PostgreSQL 16 como banco principal. Contexto: dados relacionais com multi-tenancy, JSON para configs, transações ACID. Decisão: PostgreSQL 16 via Docker, Prisma como ORM/migrations. Sem NoSQL na Fase 0-3. Trade-off: self-hosted aumenta responsabilidade operacional.

**`docs/decisions/ADR-006-auth-jwt-proprio.md`** — Auth próprio com NestJS Passport + JWT + argon2. Contexto: evitar dependência de Auth0/Clerk ($$$), manter controle total sobre fluxo de auth e dados. Decisão: JWT próprio; argon2 para hash de senhas; otplib para 2FA. JWT só identifica — autorização revalida a cada request com cache Redis 60s. Trade-off: responsabilidade de implementar reset de senha, 2FA, etc.

**`docs/decisions/ADR-007-storage-minio.md`** — MinIO self-hosted como object storage. Contexto: armazenar PDFs, fotos de OS, logos de empresa. S3 seria $$ em escala, mas no início o custo de storage é baixo. Decisão: MinIO S3-compatible self-hosted no mesmo VPS. Migrar para S3 quando necessário sem mudança de código. Trade-off: operacional (backup, espaço em disco).

**`docs/decisions/ADR-008-billing-asaas.md`** — Asaas como gateway de pagamento. Contexto: precisa de Pix, boleto e cartão no Brasil sem custo upfront. **`docs/decisions/ADR-009-deploy-vps-docker.md`** — Deploy via Docker Compose em VPS própria (Hostinger KVM1). Contexto: custo ≈ R$0/mês até ~50 tenants em serverless seria caro; VPS é previsível. Decisão: Hostinger KVM1, Docker Compose, Caddy como reverse proxy com HTTPS automático. Upgrade para KVM2 quando necessário. Trade-off: sem auto-scaling; aceitável para 0-50 tenants.

**`docs/decisions/ADR-010-money-decimal.md`** — Valores monetários como Prisma.Decimal / string decimal / Decimal.js. Contexto: erros de ponto flutuante em cálculos financeiros são inaceitáveis. Decisão: Prisma.Decimal no backend, string decimal no JSON da API, Decimal.js no mobile/web. Nunca `number` ou `float` para valores monetários. Trade-off: verbosidade e necessidade de conversão explícita.

**`docs/decisions/ADR-011-multi-tenant-company-id.md`** — Multi-tenancy por company_id em todas as tabelas. Contexto: múltiplas empresas no mesmo banco; isolamento de dados obrigatório. Decisão: company_id como coluna obrigatória em toda tabela de negócio (sem schema por tenant). Row-level isolation via TenantGuard no NestJS. Trade-off: risco de query sem filtro de tenant — mitigado via TenantGuard obrigatório e testes de isolamento em CI.
