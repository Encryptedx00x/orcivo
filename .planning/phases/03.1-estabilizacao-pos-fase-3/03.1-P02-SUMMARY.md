## Garantias de segurança provadas (T08/T09, 35 testes A/B)

Com dois tenants reais A/B, um TECNICO e um ADMIN em A:

- **Leitura/list/detail cross-tenant** → `GET /customers` de A não vê linhas de
  B; `GET /{customers,quotes,work-orders,catalog}/:idB` → **404**.
- **Update/delete/mutation cross-tenant** → `PATCH /catalog/:idB`,
  `PATCH /work-orders/:idB`, `POST /quotes/:idB/send`,
  `PATCH /quotes/:idB/cancel`, `DELETE /catalog/:idB` → **404**.
- **Nested** → `GET /work-orders/:idB/photos` → **404**.
- **IDs relacionados (R-TEN-01)** → A não consegue criar quote/work-order/
  payment/appointment/customer referenciando `customer_id`, `catalog_item_id`,
  `work_order_id` ou `assigned_to_user_id` de B → **404** em todos.
- **Invites (G-1)** → A não lista convites de B; `DELETE /invites/:idB` de A →
  **404**; o convite de B continua `PENDING`; o token do convite ainda funciona
  para o destinatário certo.
- **RBAC (G-4)** → TECNICO recebe **403** em `GET /company/members`,
  `PATCH /company/approval-methods`, `POST /invites`, `POST /billing/checkout`,
  `POST /payments`. TECNICO **pode** `GET /payments` e criar customer.
  ADMIN/OWNER passam nas rotas admin.
- **Fail-closed** → sem `Authorization` → **401**; bearer inválido → **401**;
  rota pública (`/quotes/public/:token`, `/health`) → **200** sem contexto.
- Todas as negações são **404/403 sem corpo** — nada de B é observável.

## Bug corrigido de passagem

`auth.service.signRefresh` gerava um JWT determinístico `{sub,email,iat,exp}`;
dois refresh tokens emitidos para o mesmo usuário no mesmo segundo colidiam no
`token_hash` (unique). Adicionado `jti: crypto.randomUUID()`. Sem isso os testes
de fixture (dois signups rápidos) e logins concorrentes reais quebravam.

## T11 — spec para a próxima execução

**Objetivo:** replay de mutation mobile não duplica efeito; retry devolve a
mesma resposta. Não inventar segundo mecanismo — usar `X-Client-Request-Id` +
uma tabela `RequestIdempotency`.

**Inventário mobile (atual):**
- `apps/mobile/src/services/api.ts` — `post`/`patch`/`delete`/`postFormData`
  já injetam `X-Client-Request-Id: Crypto.randomUUID()`. **Problema:** o id é
  gerado *por chamada*, não *por operação* → um retry gera id novo → não é
  idempotente entre retries. O id precisa ser criado uma vez na camada de
  serviço/tela e reusado no retry.
- Call sites fora de `api.ts`: `screens/clientes/ClienteCreateScreen.tsx:23`
  (`api.post('/customers')`), `contexts/AuthContext.tsx:54`
  (`api.post('/auth/logout')` — ignorar, sem efeito). Os demais serviços
  (`catalog.service.ts`, `quote.service.ts`, `work-order.service.ts`) chamam
  `api.post/patch/delete` — herdam o problema do id-por-chamada.

**Backend a fazer:**
1. Model `RequestIdempotency` (`id`, `company_id`, `key` = header, `method`,
   `path`, `status_code`, `response_json Json`, `created_at`;
   `@@unique([company_id, key])`). Migration aditiva, verificada em DB efêmero.
2. Interceptor/guard: se `X-Client-Request-Id` presente numa mutation
   autenticada → `findUnique` por `(company_id, key)`; se existe, devolver
   `response_json` com `status_code` (replay); senão executar, e após sucesso
   gravar (upsert; `P2002` numa corrida → devolver o registro existente).
3. Aplicar às rotas de mutation tenant-scoped (todas exceto `@Public`).
4. Testes: 2 requests concorrentes com o mesmo id → exatamente 1 efeito +
   corpos idênticos; retry sequencial → mesma resposta; ids diferentes →
   2 efeitos.

**Mobile a fazer:**
- Gerar o `requestId` uma vez por operação lógica (na service ou no hook de
  mutation), passar como arg opcional para `api.post/patch/delete`, reusar no
  retry. `api.ts` usa o id recebido ou gera um se ausente.
