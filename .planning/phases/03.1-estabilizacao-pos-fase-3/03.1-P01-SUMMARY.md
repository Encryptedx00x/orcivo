## Validação de migrations (T09) — PostgreSQL efêmero descartável

Guard `assert-ephemeral-db.mjs` confirmou o alvo antes de qualquer write.
Containers `postgres:16-alpine` descartáveis, removidos ao fim.

### Caminho A — migrate-from-zero

```
DATABASE_URL = postgresql://***:***@localhost:55432/orcivo_verify_p01
npx prisma migrate deploy      → 4 migrations aplicadas, "All migrations have been successfully applied"
npx prisma migrate status      → "Database schema is up to date!"
npx prisma migrate diff --from-url <db> --to-schema-datamodel prisma/schema.prisma --exit-code
                               → "No difference detected." (exit 0)
psql \dt                       → payments, appointments presentes
psql pg_type                   → PaymentMethod, PaymentStatus, AppointmentType presentes
```

### Caminho B — upgrade desde o último baseline versionado

Feito com schema+migrations copiados para `$TEMP` (repo real intocado).

```
1. migrate deploy só das 3 migrations pré-P01 (até 20260527000000)
2. seed representativo: 1 company (MAIS), 1 user, 1 customer, 1 quote (total 100.00)
3. migrate deploy da 4ª migration (20260901000000)  → "successfully applied"
4. dados preservados: SELECT → 1 company, 1 customer, quotes.total = 100.00 (intacto)
5. novas tabelas usáveis: INSERT em payments (FK → quote q1) e appointments (FK → user u1) → OK
6. integridade FK: INSERT payments com company_id inexistente → "violates foreign key constraint payments_company_id_fkey"
7. migrate diff <upgrade-db> vs schema.prisma → "No difference detected." (exit 0)
```

Migration 4 é 100% aditiva (CREATE TYPE/TABLE/INDEX + ALTER ADD CONSTRAINT só nas
tabelas novas) — não pode tocar linhas existentes.

## Fora de escopo (para waves seguintes)

- Tenant hardening das colunas soltas (`payments.work_order_id/quote_id`,
  `appointments.work_order_id/created_by_user_id`) e constraints compostas
  `(company_id, id)` → **P02** (R-TEN-01).
- CI `backend.yml` ainda usa `prisma db push --force-reset` para o schema de
  teste. Trocar por `migrate deploy` é ajuste de P08 (baseline de qualidade) —
  registrado aqui, não alterado nesta wave para não misturar escopo.
- `ADR-013` e `ARCHITECTURE-MOLD.md` descrevem `db push --force-reset` no CI;
  atualizar junto com a troca do CI em P08.
- Lint/typecheck/build vermelhos herdados → **P08**. Esta wave só corrigiu a
  resolução do `parserOptions.project` do backend (bloqueava commits).
