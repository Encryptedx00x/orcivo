# 03.1-P01 — Migrations e Reprodutibilidade

## Objetivo

Fazer schema, migrations, exemplos de ambiente, Compose, Prisma e imagem backend reproduzirem uma instalação limpa sem `db push` e sem depender de artefatos locais.

## Arquivos prováveis

- `prisma/schema.prisma`, `prisma/migrations/**`, testes/scripts de migration.
- `infra/docker-compose.dev.yml`.
- Examples de ambiente do backend, web e mobile, sem valores reais.
- `apps/backend/Dockerfile`, package scripts e configuração Prisma.
- `packages/shared-types/package.json` e build output esperado.
- Runbook local e documentação de Asaas somente por nomes de variáveis.

## Dependências

- P00 aprovado e standalone ativo.
- PostgreSQL efêmero/descartável para criação/verificação.
- Nenhuma conexão com banco dev/produção durante os testes.

## Riscos

R-DB-01, R-DB-02, R-RUN-01 e R-ENV-01. Migrations existentes podem não representar todo o schema; Docker pode passar localmente apenas por volumes/cache.

## Testes automáticos

```powershell
$env:DATABASE_URL = $env:ORCIVO_EPHEMERAL_DATABASE_URL
if ([string]::IsNullOrWhiteSpace($env:DATABASE_URL) -or
    $env:DATABASE_URL -notmatch '/orcivo_(test|verify|uat)_[^?]+') {
  throw 'DATABASE_URL não identifica um banco Orcivo efêmero aprovado.'
}

npx prisma validate
npx prisma migrate status
docker compose -f infra/docker-compose.dev.yml config --quiet
docker build -f apps/backend/Dockerfile .
```

Além disso: criar PostgreSQL efêmero com nome inequívoco; provar que o guard aborta uma URL dev antes de qualquer write; rodar `prisma migrate deploy` do zero; construir uma fixture no último baseline versionado e aplicar o upgrade preservando relações/valores; comparar schema esperado; iniciar container backend sem bind mounts e chamar `/health`. Registrar URL somente de forma redigida, comandos exatos e exit codes no summary.

## Testes humanos

- Seguir o runbook em PowerShell a partir de clone limpo.
- Confirmar que nenhum passo pede `db push`.
- Confirmar que exemplos explicam IP/portas sem segredo.

## Critérios de aceite

- Payment e Appointment são criados por migrations versionadas.
- Schema e migrations não têm drift conhecido.
- Base vazia sobe só com migrate deploy.
- Upgrade do último baseline versionado preserva dados representativos.
- Docker backend gera/usa Prisma e shared-types corretamente.
- Ambiente local sobe com um comando documentado e health responde.
- Examples têm somente placeholders; nenhum `.env` real foi lido/alterado.

## Rollback

Antes de aplicar fora de DB efêmero, reverter arquivos/migration não publicada pelo commit normal. Depois de qualquer aplicação aprovada, corrigir somente com migration forward; nunca resetar ou apagar banco. Restaurar Dockerfile/docs pelo revert do commit se necessário.

## Commit sugerido

`fix(infra): restore migration and container reproducibility`

## Não fazer

- Não usar `prisma db push` como solução.
- Não aplicar migration em dev persistente/produção sem aprovação.
- Não editar `.env` real ou embutir Asaas key.
- Não depender de node_modules/dist do host no Docker.
- Não mascarar drift com baseline manual.
