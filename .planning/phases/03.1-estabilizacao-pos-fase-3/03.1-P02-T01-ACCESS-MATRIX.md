# 03.1-P02-T01 — Matriz de Acesso (rota × auth × tenant × papel)

## Guards globais (app.module.ts)

Ordem de execução NestJS: **globais → controller → rota**.

1. `JwtAuthGuard` (global) — valida JWT; respeita `@Public()`; popula `req.user = { userId, ... }`.
2. `SubscriptionStatusGuard` (global) — bloqueia mutations se `isBlocked`; respeita `@Public()` e `@AllowPastDue()`.
3. `TenantGuard` (**por-controller**, `@UseGuards(JwtAuthGuard, TenantGuard)`) — resolve membership → `req.companyId`. **Não expõe `role`.**

**Não existe** `RoleGuard` nem `@Roles` em lugar nenhum (`grep` = NONE). RBAC server-side = 0% implementado. O enum `MemberRole` (OWNER/ADMIN/TECNICO) nunca é checado.

## Gaps críticos

### G-1 — `InviteController` sem `TenantGuard` (R-TEN-01, Crítico)

`invite.controller.ts` não tem `@UseGuards`. O `JwtAuthGuard` global popula
`req.user`, mas **nada popula `req.companyId`** → fica `undefined`.

- `list()` → `companyInvite.findMany({ where: { company_id: undefined } })` — no
  Prisma, `undefined` = **sem filtro** → retorna convites (com `token`!) de
  **todas as empresas**.
- `revoke(id)` → `companyInvite.update({ where: { id } })` sem escopo de empresa
  → revoga convite de qualquer tenant.
- `create()` → `enforceLimit(undefined)`, `findFirst({ company_id: undefined })`
  → cria convite atribuído a `company_id: undefined` (falha de FK NOT NULL, mas o
  vazamento de leitura já aconteceu antes).

**Fix (P02-T04):** `@UseGuards(JwtAuthGuard, TenantGuard)` no controller +
`TenantRequest` real. Testes negativos A/B em T08.

### G-2 — Ordem de guards: `SubscriptionStatusGuard` roda antes do `TenantGuard` (R-TEN-02, B6)

Globais executam antes dos guards de controller. Logo
`subscription-status.guard.ts:35` lê `req.companyId` **sempre `undefined`** →
linha 36 `if (!companyId) return true` → **o bloqueio de inadimplência nunca
dispara** em nenhuma rota.

**Fix (P02-T03):** mover a resolução de tenant para um guard global (ou
`APP_GUARD` ordenado após um `TenantGuard` global), ou o `SubscriptionStatusGuard`
resolver o companyId por conta própria. Deny-by-default quando `companyId`
faltar em mutation autenticada.

### G-3 — Webhook Asaas fail-open (R-BIL-01, Crítico)

`webhook.controller.ts:35` — `if (this.webhookToken && token !== ...)`. Token
vazio → checagem pulada → qualquer origem injeta eventos de billing.

**Fix (P06, referenciado aqui):** fail-closed no startup se o token não estiver
configurado em produção; nos testes, fake local.

### G-4 — RBAC inexistente (R-AUTHZ-01, Crítico)

Nenhuma rota administrativa (members, approval-methods, checkout, billing,
financeiro, invite) distingue `OWNER`/`ADMIN` de `TECNICO`. Um `TECNICO` pode
convidar membros, mudar métodos de aprovação e iniciar checkout.

**Fix (P02-T02/T05):** `RoleGuard` + `@Roles(...)`; `TenantGuard` passa a expor
`req.role`.

## Ownership de IDs relacionados (R-TEN-01) — a validar em T06

Rotas que aceitam IDs de outras entidades no body e precisam checar
`company_id` do alvo **antes de gravar**: #15, #25, #39, #43 (e updates de
#17-21, #30-37). Hoje os controllers só passam `req.companyId`; os services
precisam confirmar que `customer_id`, `catalog_item_id`, `quote_id`,
`work_order_id`, `assigned_to_user_id` pertencem à mesma empresa.

## Decisão Nível B — mapeamento de papéis (adianta P02-T02)

**Registro da decisão** (research: schema `prisma/schema.prisma:99-103`,
`docs/PLANEJAMENTO_FINAL...` §8, ADR-011, ADR-013):

| Conceito de produto | Papel no schema | Regra |
|---|---|---|
| "dono" / proprietário | `OWNER` | 1 por empresa; criado no signup step 2; não removível via invite |
| "administrador" | `ADMIN` | pode: convidar/revogar, mudar approval-methods, checkout/billing, financeiro, equipe |
| "membro" / técnico | `TECNICO` | pode: CRUD de customer, catalog, quote, work-order, appointment, payment do próprio escopo; **não** pode ações administrativas acima |
| "master" (admin global Orcivo) | **fora do enum / fora de `company_members`** | identidade global separada; **nenhum** acesso concedido por role de empresa; entra por `apps/admin` com auth própria (Fase 4). P02 apenas garante que master não é modelado como membership tenant. |

- **`TECNICO` = "member"**: sim. É o papel default (`@default(TECNICO)`), o que
  recebe invite sem role explícita, e o piso de permissão.
- **`OWNER` vs `ADMIN`**: `OWNER` = superset de `ADMIN` + é imutável/único.
  RBAC trata `[OWNER, ADMIN]` como "admin-capable"; ações destrutivas de
  empresa (deletar empresa, trocar owner) ficam `OWNER`-only (fora do escopo
  P02, não há rota ainda).
- **Deny-by-default**: rota sem `@Roles` explícito e sem classificação = negada
  para `TECNICO` em mutations administrativas só quando o `RoleGuard` estiver no
  pipeline; rotas de domínio comum permanecem abertas a qualquer membro ativo.
- **Reversível**: `RoleGuard` + decorators; nenhuma migration de dados. Sem
  mudança na estratégia multi-tenant (continua `company_id`).
