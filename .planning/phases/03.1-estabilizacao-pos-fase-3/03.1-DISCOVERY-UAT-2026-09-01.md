### D-2 · PIX não salva — **MOCK/PLACEHOLDER (frontend) + FEATURE INCOMPLETA (backend)**

### D-4 · Transições de estado sem histórico e sem correção — **REQUISITO NOVO**

**Modelo atual:**

- **Quote** (`packages/shared-types/src/quote/quote-status.enum.ts`):
  ```
  DRAFT     → SENT, CANCELLED, EXPIRED
  SENT      → APPROVED, REJECTED, CANCELLED, EXPIRED
  APPROVED / REJECTED / CANCELLED / EXPIRED → []   (terminais absolutos)
  ```
  `assertValidTransition` já impede select irrestrito. **Mas:** nenhuma volta —
  não dá para reabrir um `CANCELLED`/`REJECTED`, nem corrigir um `APPROVED`
  errado. `quote.service.cancel` grava `notes = reason` (sobrescreve as notas!) e
  **não** registra audit trail (só `approve` registra).
- **WorkOrder** (`work-order.service.ts` `WO_TRANSITIONS`):
  ```
  PENDING     → IN_PROGRESS, CANCELLED
  IN_PROGRESS → DONE, CANCELLED
  DONE / CANCELLED → []   (terminais absolutos)
  ```
  Sem reabrir (`DONE por engano`), sem un-cancel. Web já constrange os botões
  (bom), mas não há caminho de correção. **Nenhuma transição de OS grava audit.**

**Requisito aprovado:**

1. Transições explícitas por **ação de domínio**, não select livre:
   - Quote: `enviar`, `aprovar` (público), `recusar/perder` (`REJECTED` com
     motivo), `cancelar` (com motivo), `reabrir` (`CANCELLED`/`REJECTED`/`EXPIRED`
     → `DRAFT` ou `SENT`), `expirar` (job).
   - WorkOrder: `iniciar`, `concluir`, `cancelar` (com motivo), `reabrir`
     (`DONE`/`CANCELLED` → `IN_PROGRESS` com motivo obrigatório), `corrigir`
     (ajuste operacional pós-encerramento — registrado, não apaga histórico).
2. Estados terminais deixam de ser dead-ends: passam a ter transições de
   **correção/reabertura** controladas (motivo obrigatório, possivelmente
   `@AdminOnly` para reabrir).
3. **Toda transição** grava audit trail (D-5): entidade, estado anterior, estado
   novo, ação, motivo, usuário, empresa, timestamp, metadata.
4. **Histórico nunca é apagado.** `quote.service.cancel` para de sobrescrever
   `notes`; o motivo vai para o audit trail.
5. A "criação automática de OS na aprovação" (`quote.service.approve`) precisa ser
   idempotente com o audit (já tratado parcialmente em P02-T11 e planejado em
   P04).

- **Fase:** 03.1-P04 (aprovação atômica) **expandida** para cobrir a máquina de
  estados completa de Quote + WorkOrder + as transições de correção; audit trail
  em D-5. Ver `ADR-016`.

### D-5 · Trilha de auditoria de negócio — **REQUISITO NOVO / FEATURE INCOMPLETA**

- **Modelo:** `AuditLog { company_id, actor_type, action, entity_type,
  entity_id, metadata Json?, created_at }` — sem `actor_user_id`, sem
  `previous_state`/`new_state` estruturados.
- **Escrito em EXATAMENTE 1 lugar:** `quote.service.approve` →
  `action: 'quote.approved'`, `actor_type: 'SYSTEM'`.
- **Não há audit para:** quote enviado/cancelado/recusado/expirado, OS
  status (todos), payment criado/baixado/removido, invite criado/revogado,
  membership aceita, approval-methods alterado, perfil da empresa alterado.
- **Não há endpoint de leitura** de `AuditLog`, nem UI (as abas "Histórico" em
  `ClienteDetail` e o bloco "Histórico" no OS detail são placeholders estáticos).
- **Não confundir com logs técnicos** (Nest logger) — isso é trilha de negócio.
- **Requisito:** trilha útil para "entender depois o que aconteceu", cobrindo no
  mínimo orçamentos, OS, pagamentos, mudanças de status, aprovação/cancelamento
  e mudanças administrativas relevantes.
- **Proposta (ver `ADR-015`):**
  - `AuditLog` ganha `actor_user_id String?` e `metadata` padroniza
    `{ from, to, reason?, ... }` para transições.
  - `AuditService.record({...})` central, chamado por quote/work-order/payment/
    invite/company services em toda mutation relevante, dentro da mesma
    transação quando houver.
  - `GET /audit-logs?entity_type=&entity_id=` (`@AdminOnly`) + tab "Histórico"
    real no web (cliente, orçamento, OS).
  - `actor_type`: `USER` | `SYSTEM` | `PUBLIC` (aprovação por link).
- **Fase:** nova wave **03.1-P07.5 — Trilha de auditoria de negócio** (entre P07
  e P08), ou expansão de P07. Migration aditiva (`actor_user_id`).

### D-9 · "Editar cliente" (web) chama endpoint inexistente — **BUG**

- **Onde:** `apps/web/app/(app)/clientes/[id]/editar/page.tsx:91` →
  `fetch('/api/customers/${id}', { method: 'PATCH' })`.
- **Backend:** `CustomerController` só tem `@Get()`, `@Post()`, `@Get(':id')`.
  **Não há `@Patch(':id')` nem `@Delete(':id')`.** → a edição sempre retorna
  erro ("Erro ao salvar. Tente novamente.").
- A tela foi marcada "✅ Fiel" no snapshot de 2026-06-05 — é fidelidade visual
  sem backing real.
- **Ocorrência similar:** mesma classe de D-2 (form que parece funcionar, sem
  endpoint por trás).
- **Fix:** `PATCH /customers/:id` + `DELETE /customers/:id` (soft delete) no
  backend, tenant-scoped + ownership, com audit trail (D-5). DTO já existe
  (`CustomerCreateSchema` reusado no front).
- **Fase:** 03.1-P07.
