## T12 — Aplicar migrations no banco persistente (HUMAN_APPROVAL)

`prisma migrate deploy` aplica, em ordem, o que ainda não estiver registrado em
`_prisma_migrations`. Rode `npx prisma migrate status` primeiro para ver o que
falta. Migrations no repo (commit `7628802`):

|---|---|---|---|

- Nenhuma é destrutiva: só `ADD COLUMN`, `CREATE TABLE/INDEX`, `ADD CONSTRAINT`
  e um `UPDATE` de backfill (migration 5).

### 2. O único ponto que toca dados existentes — migration 5 (backfill)

```sql
ALTER TABLE "quote_items"     ADD COLUMN "company_id" TEXT;
UPDATE "quote_items" qi SET "company_id" = q."company_id"
  FROM "quotes" q WHERE q."id" = qi."quote_id";
ALTER TABLE "quote_items"     ALTER COLUMN "company_id" SET NOT NULL;
-- idem para quote_approvals
```

- O `UPDATE` preenche a nova coluna a partir da empresa do orçamento pai.
- Todo `quote_item`/`quote_approval` tem um `quote_id` válido (FK existente), então
  o backfill é determinístico e o `SET NOT NULL` não falha — **exceto** se houver
  linha órfã (não deveria existir). O passo de verificação abaixo checa isso ANTES.
- Não há `DELETE`, `DROP`, `TRUNCATE`, nem alteração de valores existentes.

### 4. Procedimento exato de aprovação e aplicação (executado por humano com H-DB)

Pré-requisitos: aprovação humana explícita do gate **H-DB** (RISK_REGISTER);
backup do banco persistente **antes** de qualquer alteração.

```bash
# --- na VPS, como usuário não-root ---
cd /opt/orcivo
git fetch origin && git log --oneline origin/main -3   # confirmar commit 7628802 (ou mais novo)

# 0. BACKUP (obrigatório antes de aprovar)
docker compose -f infra/docker-compose.yml exec -T postgres \
  pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB" | gzip > ~/orcivo-preP02-$(date +%Y%m%d-%H%M%S).sql.gz

# 1. Ver o que falta (read-only)
git pull origin main
cd infra && docker compose up -d --build backend
docker compose exec backend npx prisma migrate status

# 2. Pré-checagem de órfãos do backfill (read-only — deve retornar 0/0)
docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
"SELECT (SELECT count(*) FROM quote_items qi LEFT JOIN quotes q ON q.id=qi.quote_id WHERE q.id IS NULL) AS orphan_items,
        (SELECT count(*) FROM quote_approvals qa LEFT JOIN quotes q ON q.id=qa.quote_id WHERE q.id IS NULL) AS orphan_approvals;"
# Se != 0/0: PARAR. Escalar — saneamento de dados é decisão humana separada.

# 3. Aplicar (idempotente; só aplica o que falta)
docker compose exec backend npx prisma migrate deploy

# 4. Reiniciar o backend para pegar o client novo (já embutido na imagem do passo 1)
docker compose restart backend
```

### 5. Verificação pós-aplicação

```bash
cd /opt/orcivo/infra

# a) status: "Database schema is up to date!"
docker compose exec backend npx prisma migrate status

# b) sem drift entre banco e schema
docker compose exec backend npx prisma migrate diff \
  --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --exit-code
# exit 0 = OK; exit 2 = drift (PARAR)

# c) backfill íntegro (deve retornar 0/0 — nenhuma linha sem company_id)
docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
"SELECT (SELECT count(*) FROM quote_items WHERE company_id IS NULL) AS ni,
        (SELECT count(*) FROM quote_approvals WHERE company_id IS NULL) AS na;"

# d) backfill correto (company_id do item == company_id do quote pai — deve retornar 0)
docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
"SELECT count(*) FROM quote_items qi JOIN quotes q ON q.id=qi.quote_id WHERE qi.company_id <> q.company_id;"

# e) tabela de idempotência existe e está vazia
docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
"SELECT count(*) FROM request_idempotency;"

# f) health
curl -fsS https://api.<dominio>/health   # {"status":"ok",...}

# g) smoke funcional mínimo: login + GET /quotes com um usuário real → 200, dados corretos
```

### 6. Rollback (se algo falhar)

- Migrations aplicadas **não** têm `down`. Reverter = restaurar o dump do passo 0
  **ou** aplicar uma migration forward corretiva (nunca `migrate reset` em
  persistente).
- Se só o `deploy` falhou no meio: Prisma para na migration que falhou e a
  registra como `failed`; corrija e rode `migrate resolve --rolled-back <nome>`
  **ou** restaure o backup. Não seguir sem decisão humana.

## T13 — MANUAL_UAT A/B (bloco B) — checklist

Executado por pessoa, com evidência (print/resposta HTTP) por item. Requer **duas
empresas** A e B, e em A um usuário **OWNER**, um **ADMIN** e um **TECNICO**.
Ambiente: local (`docker-compose.dev.yml` + `.env`) ou staging — **nunca** rodar
UAT que crie/mexa em dados contra o banco de produção sem base descartável.

### Setup
- [ ] Criar empresa A (signup 2 etapas) → login como OWNER de A.
- [ ] Criar empresa B (outro e-mail) → login como OWNER de B.
- [ ] Em A: convidar `ADMIN` e `TECNICO`, aceitar os convites, logar cada um.
- [ ] Em B: criar 1 cliente, 1 item de catálogo, 1 orçamento (enviar → gera token), 1 OS.
- [ ] Anotar os IDs e o token público de B.

### B-1 · Isolamento de leitura (API)
- [ ] `GET /customers` como A → **não** aparece nenhum cliente de B.
- [ ] `GET /customers/{idClienteB}` como A → **404** (não 403), corpo vazio.
- [ ] `GET /quotes/{idQuoteB}` como A → **404**.
- [ ] `GET /work-orders/{idOSB}` como A → **404**.
- [ ] `GET /catalog/{idCatalogB}` como A → **404**.
- [ ] `GET /work-orders/{idOSB}/photos` como A → **404**.

### B-2 · Isolamento de escrita / IDs relacionados (API)
- [ ] `PATCH /catalog/{idCatalogB}` como A → **404**.
- [ ] `POST /quotes/{idQuoteB}/send` como A → **404**.
- [ ] `POST /quotes` como A com `customer_id` = cliente de B → **404**.
- [ ] `POST /quotes` como A com `catalog_item_id` = item de B → **404**.
- [ ] `POST /work-orders` como A com `assigned_to_user_id` = usuário de B → **404**.
- [ ] `POST /payments` como ADMIN de A com `work_order_id` = OS de B → **404**.

### B-3 · Convites (API)
- [ ] `GET /invites` como A → não lista convites de B.
- [ ] `DELETE /invites/{idConviteB}` como A → **404**; o convite de B continua `PENDING`.
- [ ] Aceitar o convite de B com o token → funciona para o destinatário certo.

### B-4 · RBAC (API)
- [ ] TECNICO de A: `GET /company/members` → **403**.
- [ ] TECNICO de A: `PATCH /company/approval-methods` → **403**.
- [ ] TECNICO de A: `POST /invites` → **403**.
- [ ] TECNICO de A: `POST /billing/checkout` → **403**.
- [ ] TECNICO de A: `POST /payments` → **403**; `GET /payments` → **200**.
- [ ] TECNICO de A: `POST /customers` → **201** (rota de domínio).
- [ ] ADMIN de A: `GET /company/members` → **200**.
- [ ] OWNER de A: `PATCH /company/approval-methods` → **200**.

### B-5 · Fail-closed (API)
- [ ] `GET /customers` sem header `Authorization` → **401**.
- [ ] `GET /customers` com token inválido → **401**.
- [ ] `GET /quotes/public/{tokenB}` sem auth → **200** (rota pública correta).
- [ ] Inspecionar corpos dos 404/403 acima → **nenhum dado de B** vaza (sem nome,
      total, número, etc.).

### B-6 · Idempotência (API)
- [ ] `POST /customers` com `X-Client-Request-Id: X` e corpo Y → **201**; repetir
      idêntico → **201** com o **mesmo** `id`; `GET /customers` mostra **1** linha.
- [ ] Mesmo `X-Client-Request-Id` com corpo diferente → **409**.
- [ ] Dois `POST /customers` simultâneos com o mesmo id → **1** cliente criado
      (uma resposta 201, a outra 201-replay ou 409).
- [ ] `POST /work-orders/{id}/photos` (multipart) 2× com o mesmo id → **1** foto.
- [ ] `POST /quotes/{id}/send` 2× com o mesmo id → 2ª é replay (não regenera token/PDF, não erra "transição inválida").

### B-7 · Web (`app.<dominio>` ou `localhost:3001`)
- [ ] Logado em A, tentar abrir `/(app)/clientes/{idClienteB}` na URL → erro/404,
      sem dados de B.
- [ ] Logado em A, tentar `/(app)/orcamentos/{idQuoteB}` → erro/404.
- [ ] Como TECNICO de A: a tela de Equipe / convites / métodos de aprovação /
      checkout **não** deixa executar a ação (bloqueio server-side confirma 403,
      não só a UI escondendo o botão).
- [ ] Abrir o link público `/approve/{tokenB}` em aba anônima → carrega a proposta
      de B sem exigir login (rota pública correta).

### B-8 · Mobile (Expo Go / build)
- [ ] Logado em A, nenhuma tela lista clientes/orçamentos/OS de B.
- [ ] Criar cliente/orçamento no mobile com rede instável / duplo-toque no botão
      → **1** registro criado (idempotência via `X-Client-Request-Id`).
- [ ] Enviar orçamento (gera PDF/token) com retry após timeout → **não** cria 2º
      token nem erro de transição.
- [ ] Upload de foto de OS com retry → **1** foto.
- [ ] Como TECNICO no mobile: ações administrativas (se acessíveis) retornam erro
      do servidor, não passam.

- [ ] Nenhum FAIL de isolamento/RBAC/idempotência.
